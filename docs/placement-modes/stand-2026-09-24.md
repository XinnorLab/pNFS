Notes.

- **Trial 2 found a contract gap** and the fix shipped mid-trial
  (`3a76e6c`, design spec §7 "Unobserved incarnation", contract manifest
  `unobserved_incarnation_rule`). The batch schema allows
  `target_incarnation: null` on a `quality = UNKNOWN` record — when the
  connector cannot read its source it knows the configured binding but
  not the share's incarnation. The MDS read the null as a changed
  incarnation → `BINDING_MISMATCH` → the DS showed `NO_BINDING`. The
  refusal was right (fail closed, no file landed), the diagnosis was
  wrong: it sent the operator to rebind a DS whose only problem was a
  stopped source. Now the tuple is compared without the incarnation,
  the record is accepted as UNKNOWN with the connector's reason codes,
  the pin is neither created nor changed by it. Trial 2R shows the
  intended picture: `quality=UNKNOWN reason=ASSESSMENT_UNKNOWN`,
  `last_detail = accepted 1`.
- Timings on this stand: agent stop → `ASSESSMENT_UNKNOWN` in 13 s
  (connector collects every 5 s, source max age 20 s, one MDS poll);
  agent start → `VALID` in 11 s; connector stop → `reachable=0` in 3 s
  (3 × 1 s poll), rows stale in 15 s (their remaining TTL); connector
  start → `VALID` in 11 s (connector readiness + hold-down). Every
  refusal window produced zero data objects on either DS; the client saw
  `ENOSPC` at `close()` (the inode exists, the LAYOUTGET/CREATE of the
  backing object was refused with `NFS4ERR_NOSPC`).
- A connector restart is a new `runtime_epoch`: the MDS logs it, resets
  the sequence lines and binding pins, and re-pins from the first VALID
  record (trial 3). No operator action was needed.
- MDS 1 in `smart` without a connector refuses every new placement in
  `shard1` (`MODE_NOT_READY`, `CONNECT` errors counted) — by design
  (per-MDS readiness). A second connector on node223 is Stage C
  (`docs/TODO.md`).
- The capacity domain the connector publishes
  (`<controller>/<fs uuid>/<fs incarnation>:/dev/xi_data`, 123 bytes)
  fits `PM_DOMAIN_ID_MAX` (128) with little room; a longer device path
  would be a record shape error. Worth a note in the profile doc
  (Stage C).
- Weight in `smart` with one covered DS at 98 % free and ppm 10⁶:
  `98 · 10⁶ · 65536 = 6422528000000`, the same figure as the `fill`
  trial 2 of 2026-09-23.
- The stand is left on the legacy configuration (row 5) with the
  `3a76e6c` binary; `mds.conf.<ts>.bak` backups on both MDS; rollback to
  the pre-Stage-A binary is `pm-deploy.sh --rollback`. The trial
  directories under `shard1`/`shard2` were removed, `/mnt/pnfs2` on
  node225 unmounted, `xinas-agent` and the connector running.
- Not measured here: LAT-25 create-throughput budget, a profile reload
  on the stand (both Stage C acceptance rows).
- Fork CI on `3a76e6c` failed once in `test_ds_connector` with SIGPIPE:
  the test's own fake server wrote into a socket the client had closed on
  purpose (the streamed-oversize case) and the signal killed the test
  process on the runner; node225 finished the write first. Test-only,
  fixed in `1bbd41d` (`send(MSG_NOSIGNAL)` + `SIG_IGN`); the MDS client
  side already used `MSG_NOSIGNAL` since review wave 2.
